6.1 문서 개요

Cropy를 실제 기기에 설치하고, 모델을 넣고, 다른 구성 요소와 연결하는 방법을 정리했다. 읽는 사람은 배포를 맡은 이서하와, 보드에서 직접 테스트해야 하는 나머지 팀원이다.

지금 바로 따라 할 수 있는 부분(Docker 배포, 기기 진단 모델 준비, 모델 교체, 문제 해결)과, 보드를 받아야 확인할 수 있는 부분(ARM64 설치, NPU, 음성)을 나눠 썼다. 보드 쪽 절차는 아직 실행해 보지 않은 계획이라 명령이 바뀔 수 있다.

6.2 배포 환경 설정

배포 대상 기기 및 OS

대상 요구 사항 상태
x86_64 PC·서버 Docker, Docker Compose, 디스크 5GB 이상 확인됨
Orange Pi 5 Plus 5 Plus 전용 OS 이미지 (ARM64 Ubuntu 계열), RKNPU 드라이버, 16GB RAM 보드 수령 후 확인
사용자 휴대폰 Android Chrome 또는 iOS Safari. 카메라·기기 진단은 HTTPS 접속 필요 실기기 확인 예정

일반 Orange Pi 5(RK3588S)용 이미지와 5 Plus(RK3588)용 이미지는 다르다. 지급받은 이미지가 있으면 먼저 그대로 부팅해서 NPU 예제가 돌아가는지 확인하고, 그 전에는 커널을 바꾸는 전체 업그레이드를 하지 않는다. RKLLM 런타임이 NPU 드라이버 버전에 민감하기 때문이다.

필요한 소프트웨어

구성 버전 비고
Python 3.13 백엔드 컨테이너 python:3.13-slim
Node.js 22 프론트 컨테이너 node:22-alpine
PyTorch / torchvision 2.13.0 / 0.28.0 CPU 빌드 requirements.txt의 +cpu 휠은 x86용. ARM64는 별도 확인

환경 변수

백엔드는 backend/.env 또는 Compose environment에서 읽는다. 기본값은 backend/app/core/config.py에 있다.

프론트의 BACKEND_ORIGIN은 환경 변수가 아니라 빌드 인자다. Next.js standalone 빌드가 rewrite 목적지를 빌드할 때 파일에 박아 넣기 때문에, 실행할 때 바꿔도 무시되고 기본값 127.0.0.1:8000으로 프록시를 시도한다. 컨테이너 안에서는 이 주소에 백엔드가 없어서 API와 사진이 전부 깨진다. 값을 바꾸려면 다시 빌드해야 한다.

docker compose build --build-arg BACKEND_ORIGIN=http://backend:8000 frontend

6.3 모델 및 추론 엔진 설치

모델 파일

모델 파일은 크기 때문에 Git에 넣지 않는다. 팀 드라이브에서 받아 아래 위치에 둔다.

파일 위치 크기 확인 방법
best_model.pth (서비스 CNN) ml/checkpoints/ 94,420,689바이트 SHA-256 b0b0b4a24af1430778a2bc15ede5cc068e200539dfeb7fc5ced02574a63d4b8b
pair_mu.pth (보조, 선택) ml/checkpoints/ 약 44.8MB ENABLE_PAIR_MODEL=true일 때만 사용
cnn-<hash>.onnx (기기 진단용) frontend/public/offline-assets/ 94,024,130바이트 manifest.json의 sha256과 비교
.rknn, .rkllm 미정 - 변환 후 추가 예정 
sha256sum ml/checkpoints/best_model.pth

해시가 다르면 다른 모델이다. 서비스 결과마다 model_version으로 해시가 남기 때문에, 해시가 바뀐 상태로 배포하면 예전 이력의 재촬영이 409로 막힌다. 이건 의도한 동작이다.

기기 진단용 ONNX 모델 만들기

개발 PC에서 한 번만 하면 된다.

cd backend
.venv\Scripts\python.exe -m pip install -r requirements-browser-export.txt
.venv\Scripts\python.exe scripts\export_browser_model.py
cd ..\frontend
npm ci
npm run build

frontend/public/offline-assets/에 cnn-<hash>.onnx, manifest.json, manifest-<bundle>.json이 생긴다. 예전 manifest-*.json은 지우지 않는다. 이미 휴대폰에 저장된 예전 기록을 동기화할 때 서버가 그 묶음 정보를 확인하기 때문이다. ONNX Runtime의 JS·WASM 파일은 빌드할 때 npm 패키지에서 public/offline-runtime/으로 복사되므로 외부 CDN이 필요 없다.

6.4 온디바이스 시스템 통합 방법

1단계: Docker로 웹앱 띄우기 (현재 방식)

git clone https://github.com/hs-cropy/Cropy.git cropy
cd cropy
# ml/checkpoints/best_model.pth 와 frontend/public/offline-assets/ 를 먼저 준비
docker compose up -d --build
curl http://localhost:3000/api/v1/ready      # 200이 나와야 실제 진단 가능

Compose는 컨테이너 두 개를 띄운다.

브라우저 ──▶ frontend:3000 ──(rewrite)──▶ backend:8000 (외부 미노출)
                                           ├─ /models        ← ml/checkpoints (읽기 전용)
                                           ├─ /offline-assets ← frontend/public/offline-assets (읽기 전용)
                                           └─ /data          ← cropcare-data 볼륨 (SQLite, 사진)

백엔드 healthcheck는 30초마다 /api/v1/ready를 부른다. 첫 기동에 모델을 올리는 시간이 있어서 start_period를 60초로 잡았다. 컨테이너를 지우고 다시 만들어도 cropcare-data 볼륨의 이력과 사진은 남는다.

서버 배포 (FR-17, 계획 · 담당 이서하)

웹 버전을 외부에서 쓰게 하려면 서버 한 대에 1단계와 같은 Docker 구성을 그대로 올린다. 백엔드는 모델을 메모리에 계속 올려 두고 SQLite와 사진을 디스크에 남겨야 해서, 서버리스가 아니라 계속 켜져 있는 VM이 필요하다.

항목 조건
서버 x86 VM, RAM 2GB 이상, 디스크 유지. 후보는 Azure for Students(카드 없이 $100 크레딧), Oracle Cloud Always Free(ARM, 카드 인증 필요)
HTTPS 프론트(3000) 앞에 Caddy 같은 리버스 프록시를 두고 자동 인증서를 받는다. 휴대폰 카메라 미리보기와 기기 진단은 HTTPS에서만 동작한다
모델 파일 best_model.pth, frontend/public/offline-assets/를 서버에 복사한 뒤 빌드한다. Git에는 없다
공개 포트 80·443만 연다. 백엔드 8000은 외부에 열지 않는다
확인 https://<도메인>/api/v1/ready 200, 휴대폰에서 촬영·진단·이력, 재시작 후 DB·사진 보존

ARM 서버(Oracle 등)를 쓰면 requirements.txt의 +cpu 휠이 맞지 않으므로 아래 2단계의 ARM64 의존성 확인을 먼저 한다. 학교 클라우드 지원비가 나오면 그쪽 서버로 옮긴다.

PWA (FR-18, 계획 · 담당 고명준)

서버 배포로 HTTPS가 생긴 뒤 앱 전체를 홈 화면에 설치할 수 있게 한다. 이미 /offline/ 범위로 등록되는 기기 진단 서비스 워커가 있으므로, 새 서비스 워커는 /offline/과 /offline-assets/를 캐시하지 않게 하거나 둘을 하나로 합친다. 두 서비스 워커가 같은 파일을 다른 캐시에 저장하면 모델이 두 번 받아질 수 있다.

라이브 시연용 로컬 실행

발표장에서는 노트북에 백엔드와 프론트를 띄우고 휴대폰을 같은 Wi-Fi로 접속시킨다. tools/live-demo/start-demo.ps1이 실제 모델로 백엔드를 띄우고, API 주소를 비워 빌드한 프론트를 0.0.0.0:3000으로 실행한 뒤, 그때의 노트북 IP로 QR을 만든다(저장소에는 아직 커밋하지 않음). http://IP 접속은 HTTPS가 아니라 카메라 미리보기와 기기 진단 준비가 막히고, 휴대폰 기본 카메라로 찍어 올리는 방식은 된다. 학교 Wi-Fi가 기기 간 접속을 막으면 노트북 핫스팟으로 바꾼다.

2단계: Orange Pi에 올리기 (예정)

진행 순서는 "CNN을 CPU로 먼저 → Qwen → 음성 → 전체 측정 → 필요하면 최적화"다. 한 번에 다 올리면 어디서 문제가 생겼는지 알기 어렵다.

  1. 장치 확인 (이서하): OS·커널·NPU 드라이버 버전, RAM, 저장장치를 기록한다.

    uname -m        # aarch64
uname -r
cat /etc/os-release
free -h

  2. ARM64 의존성 확인 (이서하): requirements.txt의 torch==2.13.0+cpu는 x86용 인덱스를 가리킨다. ARM64에서는 같은 버전의 aarch64 휠이 있는지 먼저 확인하고, 설치에 성공한 조합을 별도 파일로 고정한다. 기존 x86 설정은 건드리지 않는다.

  3. CNN CPU 풀스택 (이서하, 김헌영): Compose 또는 네이티브로 띄우고 실제 사진으로 진단·재촬영·이력을 확인한다. PC와 같은 사진을 넣어 후보와 점수가 같은지 비교한다.

    cd ~/cropy/backend
source .venv/bin/activate
APP_ENV=production ALLOW_MOCK_PREDICTIONS=false \
  uvicorn app.main:app --host 0.0.0.0 --port 8000

  4. 성능 기준선 (김헌영): 5번 문서의 측정 스크립트를 보드에서 그대로 돌린다. 단건 1초를 넘으면 RKNN 변환을 검토한다.

  5. Qwen 연결 (김헌영, 박성호): 지급 툴킷의 기본 예제로 변환→보드 응답을 먼저 확인한 뒤, 학습한 어댑터를 병합해 W8A8로 변환한다. 백엔드의 generate_guidance()에 RKLLM 호출 함수를 caller로 넣으면 연결된다. 실패하거나 10초를 넘기면 템플릿 문장이 나가므로 진단 흐름은 멈추지 않는다.

  6. 카메라·음성 (고명준): USB 카메라 촬영, 한국어 STT·TTS 예제를 단독으로 먼저 확인한다. 스피커 소리를 마이크가 다시 알아듣지 않는지도 본다.

  7. 휴대폰 접속 (이서하): 보드를 AP로 만들어 휴대폰이 접속하게 한다. 카메라와 기기 진단은 HTTPS가 필요해서, 휴대폰이 신뢰하는 인증서를 보드에 설치해야 한다. http://보드IP:3000으로는 서버 진단은 되지만 카메라 미리보기와 기기 진단 준비가 안 된다.

    nmcli device status
sudo nmcli device wifi hotspot ifname wlan0 ssid cropy password '<비밀번호>'

  8. 오프라인·자동 시작 (이서하): 인터넷을 끊은 상태에서 부팅부터 진단·재촬영·음성까지 해 본다. Compose의 restart: unless-stopped와 시스템 부팅 시 Docker 서비스와 컨테이너가 자동으로 시작되는지 확인한다.

단말 에이전트와 백엔드의 연결

단말 에이전트는 백엔드를 새로 만들지 않고 localhost:8000의 기존 API를 그대로 부른다.

버튼 입력 → 카메라 촬영 → POST /api/v1/diagnose → 결과 JSON
         → 혼동쌍이면 재촬영 안내 음성 → 두 번째 촬영 → POST /api/v1/diagnose/{id}/refine
음성 질문 → STT → Qwen 기능 선택 → handler가 DB 근거로 문장 구성 → TTS

에이전트가 지켜야 할 것은 세 가지다. 진단 요청마다 Idempotency-Key를 붙인다. recapture가 있으면 결과를 확정해서 읽지 않는다. 숫자(농약 희석배수, 사용 일수)가 들어간 문장은 DB 값과 맞는지 확인한 뒤에 읽는다.

6.5 에러 처리 및 트러블슈팅 가이드

증상 원인 해결
/ready가 503, prediction_mode: unavailable 모델 파일이 없거나 해시·클래스 매핑이 맞지 않음 ml/checkpoints/best_model.pth 위치와 SHA-256 확인. 백엔드 로그에서 체크포인트 검증 오류 확인
/ready가 503, database_connected: false DB 경로 권한, 디스크 부족 /data 볼륨 권한과 여유 공간 확인
화면은 뜨는데 API·사진이 모두 실패 프론트 빌드 때 BACKEND_ORIGIN이 잘못 들어감 빌드 인자를 확인하고 프론트 다시 빌드
로컬에서 프론트 rewrite가 ECONNREFUSED localhost가 IPv6로 해석됨 기본값 127.0.0.1:8000을 그대로 쓰거나 uvicorn을 --host 0.0.0.0으로 실행
사진 업로드가 413 100MiB 또는 2억 1천만 픽셀 초과, 앞단 프록시 본문 제한 /api/v1/capabilities에서 한도 확인. 프록시는 100MiB 이상(두 장 동기화는 200MiB 이상) 허용
HEIC·DNG 업로드가 400 해당 디코더가 지원하지 않는 압축 방식 JPEG로 다시 찍어 올리기. 기기 진단 화면은 JPEG·PNG만 처리
재촬영이 409 MODEL_VERSION_CONFLICT 1차 진단 이후 모델을 교체함 새로 진단. 정상 동작
기동이 외래키 오류로 멈춤 기존 DB에 참조가 깨진 행이 있음 서비스를 멈추고 DB를 백업한 뒤 PRAGMA foreign_key_check;로 원인 확인. 검사를 끄거나 이력을 지워서 우회하지 않음
휴대폰에서 카메라가 안 켜짐 HTTP 접속 (보안 컨텍스트 아님) HTTPS로 접속
기기 진단 "모델 준비" 실패 HTTPS 아님, 저장 공간 부족, 다운로드 중단 HTTPS 확인 후 다시 시도. 실패해도 기존 모델은 유지됨
저장 실패 안내(save_status=failed) DB 쓰기 실패 화면의 "다시 저장" 버튼. 24시간 안에 하지 않으면 만료(410)

로그와 디버깅

docker compose ps
docker compose logs --tail=100 backend
curl -i http://localhost:3000/api/v1/ready

처리되지 않은 500 오류를 빼면 모든 오류 응답에 request_id가 있고 응답 헤더 X-Request-ID와 같다. 사용자가 오류 화면을 보내 주면 이 값으로 백엔드 로그를 찾는다. 오래된 미참조 사진은 먼저 미리보기로 확인한 뒤 서비스를 멈춘 상태에서 지운다.

python scripts/cleanup_uploads.py --min-age-hours 72          # 목록만 확인
python scripts/cleanup_uploads.py --min-age-hours 72 --apply  # 실제 삭제

6.6 업데이트 및 유지보수 전략

모델 업데이트 절차

OTA 자동 업데이트는 없다. 단말이 오프라인에서 쓰이는 걸 전제로 해서, 이번 학기에는 수동 교체만 지원한다.

  1. 새 후보가 5번 문서의 합격 기준(특히 무 노균병 재현율)을 통과했는지 확인한다. 10월 6일 256 후보처럼 전체 지표만 좋은 모델은 넣지 않는다.
  2. 기존 모델 파일, .env, DB, uploads/를 함께 백업한다.
  3. 서비스를 멈춘다.
  4. 새 파일을 복사하고 SHA-256을 확인한다.
  5. 재시작한다. 모델은 프로세스 메모리에 캐시되므로 파일만 덮어쓰고 재시작하지 않으면 바뀌지 않는다.
  6. /ready 200, 실제 사진 한 장 진단, 재촬영, 이력 조회를 확인한다.
  7. 기기 진단을 쓰면 ONNX 묶음도 다시 만들고 프론트를 다시 빌드한다.

문제가 생기면 백업한 모델과 설정으로 되돌리고 재시작한다. 앞으로 단말이 인터넷에 연결될 때 모델을 받아 오는 방식을 넣는다면, 지금 기기 진단에서 쓰는 방식(SHA-256·크기·세션 생성이 모두 성공한 뒤에만 교체, 실패하면 기존 모델 유지)을 그대로 가져갈 생각이다.

버전 관리 정책

  • 코드: main(제출), develop(통합), 기능 브랜치(fe/, be/, ml/, model/, docs/, ci/). 모든 변경은 PR로 올리고, 폴더 담당자가 리뷰한다(CODEOWNERS). CI가 통과해야 병합한다.
  • 모델: 파일 이름이 아니라 SHA-256으로 구분한다. 진단 결과마다 model_version(해시)과 preprocessing_version(예: resize-224-imagenet-v1)이 저장된다.
  • 기기 진단 묶음: 모델·전처리·병해 안내·판정 기준을 묶은 bundle_version(64자리 해시). 묶음이 바뀌면 이름도 바뀌고, 예전 묶음 정보는 보존한다.
  • 판정 정책: policy_version (예: decision-v1:low=0.5). 임계값을 바꾸면 버전도 바뀐다.
  • LLM 입력 계약: schema_version 1.0.
  • 농약 카탈로그: PSIS 동기화 시각(synced_at)을 항목마다 기록한다.

모니터링 및 성능 최적화

  • 배포 직후와 모델 교체 후에 /ready와 실제 사진 진단을 확인한다.
  • 농약 카탈로그는 인터넷이 될 때 python scripts/sync_pesticides.py로 갱신한다. 일부 페이지가 빠지거나 중복이 생기면 전체 갱신을 취소하고 이전 파일을 유지한다.
  • diagnosis_requests 표와 .pending 초안은 자동으로 지워지지 않는다. 단말 저장 공간에 맞춰 보관 기간을 정하고 정리 절차를 추가해야 한다.
  • SQLite 마이그레이션 백업(.backup-*)도 자동 삭제가 없다. 단말 저장 용량을 보고 개수 제한을 정한다.
  • 성능 최적화는 보드에서 측정한 값을 보고 결정한다. 측정 전에는 스레드 수나 양자화 같은 설정을 미리 바꾸지 않는다.
