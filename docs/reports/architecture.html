2.1 문서 개요

Cropy가 어떤 구성 요소로 이루어져 있고, 사진 한 장이 들어와서 결과가 나갈 때까지 데이터가 어디를 거치는지 정리한 문서다. 팀원이 자기 파트 밖의 코드를 고칠 때 어떤 계약을 지켜야 하는지 확인하는 용도로도 쓴다.

현재 동작하는 웹앱 구조와, 보드를 받은 뒤 옮겨 갈 단말 구조를 나눠서 적었다. 단말 쪽은 아직 설계 단계라서 바뀔 수 있다.

2.2 시스템 개요

설계 목표와 원칙

  1. 진단 로직은 한 곳에만 둔다. 웹앱이든 단말이든 진단·재촬영·이력·농약 조회는 같은 FastAPI 백엔드를 호출한다. 단말용으로 로직을 새로 짜면 두 벌을 맞춰야 하는데, 5명이 남은 5주 동안 감당하기 어렵다.
  2. 모델이 확실하지 않으면 답하지 않는다. 모델 파일이 없거나 클래스 매핑이 맞지 않으면 그럴듯한 가짜 결과를 내지 않고 503을 돌려준다. 개발 중 시연용 Mock은 개발 모드에서 명시적으로 켰을 때만 동작한다.
  3. LLM은 판단하지 않고 고르기만 한다. Qwen은 사용자의 질문을 보고 어떤 기능을 부를지만 정한다. 병명, 농약 이름, 사용량 같은 사실은 CNN 결과와 DB에서만 나온다. 2B 모델이 농약 용량을 지어내는 상황은 피해야 한다고 봤다.
  4. 자원이 제한된 기기를 전제로 한다. 모델은 프로세스에 한 번만 올려서 계속 쓰고, 동시 진단은 기본 1건으로 제한한다. 보드에서 CNN·Qwen·음성이 RAM 16GB를 같이 써야 하기 때문이다.
  5. 인터넷이 없어도 진단은 된다. 농약 카탈로그는 미리 동기화해 두고 진단 때는 로컬 DB만 본다.

2.3 하드웨어 아키텍처

타겟 디바이스 구성

구성 요소 사양 Cropy에서의 용도
AP Rockchip RK3588, Cortex-A76 ×4 (최대 2.4GHz) + Cortex-A55 ×4 FastAPI, 이미지 전처리, CNN CPU 추론, STT
NPU 3코어, 합계 6 TOPS (INT8) Qwen3.5-2B (RKLLM). CNN은 CPU로 부족할 때만 RKNN으로 이전
GPU Mali-G610 MP4 현재 사용 계획 없음
메모리 LPDDR4X 16GB CNN 추론 프로세스 약 0.5GB(PC 측정), Qwen W8A8 약 2~3GB 예상, 나머지 웹·음성
저장장치 eMMC 또는 M.2 NVMe SSD OS, 모델 파일, SQLite, 사진
네트워크 2.5GbE ×2, 무선은 M.2 모듈 휴대폰 접속용 AP 모드 (모듈의 AP 지원 여부 확인 필요)
주변장치 USB 카메라, USB 마이크, 스피커, GPIO 버튼·LED 촬영, 음성 입력, 안내 출력

메모리 수치 중 CNN은 PC에서 잰 값(5번 문서 참고)이고, Qwen은 RKLLM 자료를 보고 잡은 추정치다. 보드를 받으면 첫 주에 실제 값을 다시 잰다.

하드웨어 가속기 활용 방안

NPU는 Qwen에 먼저 배정한다. 이유는 두 가지다.

  • 2B 규모 LLM은 CPU로 돌리면 응답이 너무 느려서 대화가 안 된다. NPU가 사실상 필수다.
  • 반면 ResNet50 한 장 추론은 PC CPU에서 수십~수백 ms 수준이다. A76 코어에서도 1초 목표 안에 들어올 가능성이 있어서, 먼저 CPU로 기준선을 잡아 보고 부족할 때만 RKNN INT8 변환을 한다.

CNN까지 NPU로 옮기면 Qwen과 NPU를 나눠 써야 한다. 이 경우 두 모델을 동시에 돌리지 않고 순서대로 실행하게 하고, 경합 시간을 따로 잰다.

화면 설계와 구현의 연결

화면은 김헌영이 Figma 파일(cropy)에서 설계했고, 프론트 담당자가 이를 코드로 옮기는 구조로 작업했다. Figma에는 디자인 시스템 페이지(색·서체·간격·라운드 토큰, 컨트롤·탐색·카드 상태), 모바일·데스크톱 화면, 피드백 상태 각 24종, 시나리오 S1~S5 프로토타입이 있다. 각 화면 옆에 개발 가이드를 붙여 두어서 구현하는 사람이 여백·크기·문구를 Figma에서 바로 확인할 수 있게 했다.

색은 "밭에서 쓰는" 느낌을 내려고 브라운·카키·옐로를 주색으로 잡았다(배경 #FBF8F1, 본문 #3D2F1A, 주 버튼 #F5B301). 고령 사용자의 시인성 때문에 주요 색에 파랑 계열은 쓰지 않았고, 심각도는 초록·황색·적갈색에 글자와 아이콘을 함께 붙인다. 이 토큰이 tailwind.config.js와 1:1로 대응하고, 공통 컴포넌트는 Storybook에서 상태별로 확인할 수 있다(#75).

구현할 때 디자인 시스템 페이지와 실제 화면 시안이 서로 다르면 화면 시안을 따르기로 했다(10/13 디자인 개편 구현 기획).

데이터 흐름: 1차 진단

  1. 프론트가 POST /api/v1/diagnose로 사진을 보낸다. 같은 요청을 두 번 보내도 결과가 하나만 생기도록 Idempotency-Key 헤더를 붙인다.
  2. 백엔드는 요청 본문 크기를 multipart 해석 전에 먼저 제한한다(파일 한도 + 64KiB).
  3. 실제 파일을 디코딩해서 형식을 확인한다. HEIC·RAW·WebP·AVIF나 긴 변이 4096픽셀을 넘는 사진은 JPEG로 바꿔 저장한다.
  4. CNN이 9개 클래스 전체 분포를 낸다. 응답에는 상위 3개를 쓰고, 재촬영 융합을 위해 전체 분포를 이력에 저장한다.
  5. 클래스 ID를 DB의 diseases.model_class_id와 맞춰 병해 정보와 농약을 붙인다. ID가 맞지 않으면 임의 병명으로 채우지 않고 503을 낸다.
  6. 판정 정책을 적용한다. 혼동쌍 접전이면 recapture 안내를 넣는다.
  7. 이력을 저장하고 응답한다. DB 저장만 실패하면 결과는 그대로 보여 주고 save_status=failed와 복구 토큰을 준다.

데이터 흐름: 재촬영

  1. 사용자가 안내받은 부위를 찍어 POST /diagnose/{id}/refine으로 보낸다.
  2. 저장해 둔 1차 분포와 2차 사진 분포를 정해진 가중치로 합친다. 판별 부위를 찍은 2차 사진에 더 큰 비중을 둔다.
  3. 보조 모델(pair_mu.pth)을 켜 둔 경우, 1차 상위 두 후보가 그 쌍과 같을 때만 쌍 내부 비율을 다시 나눈다. 쌍 밖 클래스 점수는 그대로 둔다.
  4. 1차 진단 때와 모델·전처리 버전이 다르면 섞지 않고 409를 낸다. 서로 다른 모델의 점수를 평균 내면 의미가 없기 때문이다.

제어 흐름과 동시성

  • 모델은 앱 시작 때 한 번 올리고 lru_cache로 계속 쓴다. 모델 파일을 바꾸면 재시작해야 반영된다.
  • 이미지 디코딩·추론·DB 작업은 작업 스레드에서 돌리고, 프로세스당 세마포어로 동시 진단 수를 막는다(기본 1).
  • 같은 이력을 두 요청이 동시에 수정하면 revision 컬럼으로 충돌을 잡아 409를 낸다.

처리 방식은 요청 단위 배치다. 영상 스트리밍 추론은 하지 않는다. 카메라 미리보기는 화면에만 보여 주고, 사용자가 촬영 버튼을 눌렀을 때 한 장만 처리한다.

개인정보와 보안 관련 흐름

  • 사진은 기기 밖 서비스로 보내지 않는다. 웹앱 단계에서는 팀이 운영하는 백엔드까지만 가고, 단말에서는 보드 안에서 끝난다.
  • 변환을 거치는 사진(HEIC, RAW 등)은 EXIF와 GPS를 복사하지 않는다. 다만 작은 JPEG/PNG는 모델 입력을 그대로 유지하려고 원본 바이트를 저장하고 있어서, 위치정보가 남을 수 있다. 이 부분은 5번 문서 결함 목록에 올렸다.
  • 현재 로그인이 없어서 이력이 모든 접속자에게 공유된다. 단말은 한 농가가 쓰는 장치라 당장은 문제가 작지만, 웹앱을 공개 배포하려면 인증이 먼저 필요하다.
  • PSIS API 키는 환경 변수로만 받고 로그·저장소에 남기지 않는다.
  • /uploads는 JPEG·PNG만 고정 MIME과 nosniff 헤더로 내보낸다. 예전에 저장된 다른 확장자 파일은 404 처리한다.
