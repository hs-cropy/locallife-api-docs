1.1 문서 개요

작성 목적 및 대상

이 문서는 Cropy가 무엇을 해야 하고, 어느 정도로 잘 해야 하는지를 팀 안에서 한 번에 맞춰 보기 위해 작성했다. 그동안 요구사항이 PRD, 웹앱 기능명세서, 스프린트 백로그에 나뉘어 있었고, 구현이 진행되면서 문서와 코드가 서로 다른 말을 하는 부분이 생겼다. 예를 들어 7주차 PRD에는 업로드 한도가 10MB로 적혀 있지만 10월 16일 모바일 사진 지원 이후 실제 기본값은 100MiB다. 이번 판에서는 이런 차이를 코드 기준으로 고쳤다.

문서 범위 및 적용 대상 시스템

  • 스마트폰 브라우저로 쓰는 Cropy 웹앱 (Next.js 프론트엔드 + FastAPI 백엔드 + PyTorch CNN)
  • 서버 없이 브라우저 안에서 모델을 돌리는 기기 진단 화면 (/offline/)
  • 최종 목표인 Orange Pi 5 Plus 독립 단말 (카메라·마이크·스피커 포함)

1.2 프로젝트 개요

프로젝트 목표 및 배경

고추·무·배추는 국내 노지에서 많이 기르는 작물이지만, 병이 생겼을 때 농가가 바로 물어볼 곳이 마땅치 않다. 농업기술센터에 사진을 보내거나 직접 찾아가야 하는데, 고령 농업인에게는 이 과정이 번거롭다. 또 밭에서는 모바일 데이터가 잘 안 터지는 경우가 있어서, 사진을 서버로 보내 결과를 받는 방식만으로는 쓰기 어렵다고 판단했다.

그래서 처음부터 "밭에서 인터넷 없이도 찍고, 결과를 듣는다"를 최종 모습으로 잡았다. 진단 모델과 안내 모델이 기기 안에서 돌아가야 사진이 외부로 나가지 않고, 통신이 끊겨도 쓸 수 있다. 이것이 온디바이스로 가는 이유다.

다만 보드가 늦게 지급되는 상황이라, 1단계는 휴대폰 브라우저로 쓰는 웹앱을 먼저 완성하고 2단계에서 Orange Pi로 옮기는 순서로 진행하고 있다.

기획 과정

기획과 화면 디자인은 김헌영이 맡았다. 9월 3일에 시나리오 스케치, 스토리보드, 프로젝트 기획서 초안, 디자인 시스템 초안을 한꺼번에 작성했고, 9월 8일에 웹앱 페이지별 기능명세서와 ERD, 4개 스프린트 백로그를 만들어 팀에 공유했다. 이 요구사항 정의서의 기능 목록도 그때의 기능명세서에서 출발했다.

기획 단계에서 정한 사용자는 세 명이다.

페르소나 특징 원하는 것 주로 쓸 형태
P1. 김수현 (67세, 무·배추 노지 30년) 스마트폰은 전화·카카오톡만 씀. 작은 글씨를 못 읽고 장갑을 낀 채 일함. 지금은 농약상에 사진을 보내고 답을 기다림 "무슨 병이고 뭘 뿌리면 되냐"를 바로 듣기 단말 (음성)
P2. 박민수 (41세, 귀농 3년차, 고추 시설재배) 스마트폰에 익숙하고 유튜브로 정보를 찾음. 등록 농약인지, 수확 전 며칠 쓰면 안 되는지 매번 헷갈림 진단 근거와 농약 사용법을 한 화면에서, 이력으로 재발 추적 웹앱
P3. 이동주 (농업기술센터 지도사) 농가를 찾아가 상담함 이력의 사진·날짜·재촬영 여부를 보면서 상담 웹앱 이력

문제 정의도 이 사람들을 기준으로 했다. P1은 글씨와 조작이 문제여서 큰 글씨와 음성 안내가, P2는 정보 찾기가 문제여서 농약 정보 연결이 요구사항으로 들어갔다. 혼동쌍 재촬영은 9월 초 모델 평가에서 오분류 44건 중 26건이 무 검은무늬병과 무 노균병 사이에서 나온 것을 보고 기획에 넣었다.

10월 7일까지는 Figma에서 모바일·데스크톱 화면을 다시 디자인하면서 확인·완료·오류·로딩 같은 피드백 상태를 모바일 24종, 데스크톱 24종으로 정리했다(사진 형식 오류, 분석 시간 초과, 저장 실패, 이력 조회 실패 등). 10월 8일에는 이 디자인을 그대로 구현하려면 백엔드에 무엇이 더 필요한지 검토했고, 그 결과로 이력 심각도 필터, 저장 실패 복구, 저장 당시 안내 보존, 판정 상태와 오류 코드 API가 추가됐다(#53, #54). 디자인 단계에서 정한 예외 상태가 기능 요구사항으로 내려온 경우다.

기대 효과

  • 사진 한 장으로 병해 후보와 대처 정보를 바로 볼 수 있다. 큰 글씨와 음성 안내로 고령 사용자도 혼자 쓸 수 있게 한다.
  • 헷갈리기 쉬운 병은 "잎 뒷면을 찍어 주세요"처럼 구체적으로 다시 찍게 해서, 한 장으로 억지로 답을 내는 것보다 덜 틀리게 한다.
  • 농약 정보는 모델이 지어내지 않고 PSIS 등록 정보만 보여 준다. 잘못된 약이나 사용량을 안내할 위험을 줄인다.
  • 단말에서는 사진이 기기 밖으로 나가지 않는다.

주요 시나리오

시나리오 A. 일반 진단 P1 김 씨가 배추 잎에서 반점을 보고 앱을 연다. 카메라 화면의 촬영 가이드에 맞춰 잎을 찍으면 분석 중 화면이 약 3초간 나온 뒤 "배추 노균병일 가능성이 가장 높습니다"라는 결과와 점수가 표시된다. 음성 안내를 켜 두었으면 결과를 읽어 준다. 아래쪽에서 예방 방법과 등록 농약 목록을 펼쳐 볼 수 있고, 결과는 이력에 자동 저장된다.

시나리오 B. 헷갈리는 병 무 잎 사진의 결과가 검은무늬병 0.46, 노균병 0.41로 거의 같게 나온다. 이 경우 앱은 결과를 확정해서 보여 주지 않고 "잎을 뒤집어 뒷면을 가까이 찍어 주세요"라고 안내한다. 뒷면에 회백색 곰팡이가 보이는 사진을 추가로 올리면 두 사진의 분포를 합쳐 결과를 다시 계산한다. 이력에는 처음 사진과 두 번째 사진이 함께 남는다.

시나리오 C. 밭에서 통신이 안 될 때 집 Wi-Fi에서 미리 "모델 준비"를 눌러 약 94MB 모델을 받아 둔다. 밭에서 데이터가 안 잡혀도 기기 진단 화면에서 사진을 찍으면 결과가 나오고 휴대폰 안에 저장된다. 집에 돌아와 "서버에 저장"을 누르면 기록이 올라간다.

시나리오 D. 단말 (목표) 보드의 버튼을 누르고 작물을 찍으면 스피커로 결과를 듣는다. "그럼 약은 뭐 써?"라고 물으면 Qwen이 농약 정보 기능을 고르고, DB에 있는 등록 정보만으로 답한다.

NFR-04 신뢰성 모델이 없거나 깨지면 가짜 결과를 내지 않고 503으로 막는다. 저장 실패, 동시 수정, 중복 요청을 구분해 처리한다 구현 (#19, #53, #81). 오류 코드 체계와 Idempotency-Key 적용
NFR-05 사용성 디자인 시스템 기준을 따른다: 본문 16px 이상(큰 글씨 모드 18px), 터치 영역 48px 이상, 글자 대비 4.5:1 이상, 심각도는 색·글자·아이콘을 함께 표시, 한 화면에 행동 1~2개, 오류 화면에는 원인과 다음 행동 버튼 구현 (#75, #78, #85). 오류 코드별 안내 문구는 10/17 커밋에서 Figma 시안대로 적용. 실제 고령 사용자 테스트는 아직 못 함
NFR-06 보안·개인정보 사진의 위치정보(GPS) 등 메타데이터를 저장 전에 제거. 비밀키를 저장소에 올리지 않음. 알려진 취약 의존성은 바로 올린다 HEIC·RAW 등 변환하는 사진은 제거됨(#83). JPEG/PNG 원본은 그대로 저장돼 GPS가 남을 수 있음. 10/17 로컬 커밋으로 고쳤지만 아직 PR 전 (5.2.4 참고). 의존성 보안 업데이트는 #71
NFR-07 확장성 클래스 ID를 폴더 앞 숫자로 고정해서 작물·병해를 추가해도 기존 ID가 밀리지 않게 한다 구현
NFR-08 배포·업데이트 모델 파일 해시와 전처리 버전을 결과마다 기록. 모델 교체 후 재시작과 준비 상태 확인 절차를 문서화 수동 절차 있음. OTA 자동 업데이트는 없음

정확도는 숫자 하나로 판단하지 않기로 했다. 10월 6일 256 해상도 후보는 전체 검증 정확도가 99.58%로 올랐는데, 정작 우리가 신경 쓰는 무 노균병 재현율은 79.17%에서 70.83%로 떨어졌다. 그래서 이 후보는 서비스에 넣지 않았다. 앞으로도 전체 정확도와 혼동쌍 클래스별 재현율을 같이 보고 판단한다.

1.6 제약사항

  • 일정: 2026년 2학기 14주. 7주차 중간 발표는 끝났고, 13~14주차에 최종 시연이 있다. 남은 기간이 약 5주라서 보드 이식과 LLM 통합을 동시에 진행해야 한다.
  • 인력: 5명. 역할은 PM·모델(김헌영), 프론트엔드(김민서), 백엔드(박성호), 카메라·음성(고명준), 디바이스·인프라(이서하)로 나눴다. 폴더별 담당자가 PR을 리뷰한다.
  • 예산: 단말 부품 40만 원 (최초 예산안 기준).
  • 하드웨어: Orange Pi 보드와 RKLLM 툴킷이 아직 지급되지 않았다. 그래서 보드 관련 수치 목표는 일단 초기값으로 두고, 측정 후 다시 정한다.
  • 데이터: 무 노균병 원천 사진이 다른 병보다 적고, 잎 뒷면을 가까이 찍은 사진은 거의 없다. 재촬영 기능의 실제 효과를 확인할 평가 자료를 따로 모아야 한다.
  • LLM 데이터 검수: 기능 토큰 학습 데이터는 AI 보조로 만든 초안이며, 사람 최종 검수가 끝나지 않았다. 검수 전 데이터로 얻은 정확도는 서비스 성능으로 말하지 않는다.
  • 전문 지식: 판별 부위 단서(포자층, 잎맥 흑변 등)는 표준 병징 자료를 보고 정리했지만, 식물병리 전문가 확인은 받지 못했다.
