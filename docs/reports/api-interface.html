4.1 문서 개요

Cropy의 각 부분이 서로 어떤 형식으로 데이터를 주고받는지 정의한다. 대상은 세 가지다.

  1. 프론트엔드·단말 에이전트가 부르는 백엔드 REST API (업무 API 12개)
  2. 백엔드 안에서 CNN 모델과 진단 서비스 사이의 함수 계약
  3. 진단 결과를 LLM에 넘기는 입력 계약과 응답 계약

API 경로와 필드는 코드에서 직접 확인했다. 9월 3일 김헌영이 만든 첫 백엔드에는 진단·재촬영·이력·병해·헬스 API만 있었고, 이후 10월 8일 Figma 디자인을 기준으로 필요한 API를 검토하면서 판정 상태, 저장 복구, 기능 조회, 오프라인 동기화가 추가됐다(#53). /ready는 박성호가 추가했고(#67), 10월 15일 입력·저장 오류 코드를 OpenAPI 명세와 맞추는 정리를 했다(#81).

4.3 API 목록 및 상세 정의

Base URL은 /api/v1이다. ID는 이 문서에서 붙인 번호다.

ID 메서드 경로 기능 주요 입력
API-01 POST /diagnose 사진 진단 multipart file, query crop_type, 헤더 Idempotency-Key
API-02 POST /diagnose/{diagnosis_id}/refine 판별 부위 사진으로 재확정 경로 ID, multipart file, Idempotency-Key
API-03 POST /results/{token}/save 저장 실패 결과 다시 저장 경로 recovery_token
API-04 GET /history 이력 목록 page, size, crop_type, severity
API-05 GET /history/{diagnosis_id} 이력 상세 경로 ID
API-06 GET /diseases 병해·정상 클래스 목록 q, crop_type
API-07 GET /diseases/{disease_id} 클래스 상세 DB 정수 ID (모델 클래스 ID와 다름)
API-08 GET /health 서버가 살아 있는지 없음
API-09 GET /ready 실제 모델·DB로 진단할 수 있는지 없음
API-10 GET /capabilities 업로드 한도, 지원 작물, 판정 기준 없음
API-11 GET /offline/manifest 브라우저용 모델 묶음 정보 없음
API-12 POST /offline/records 기기 진단 기록 동기화 multipart metadata, file, 선택 refined_file

이 밖에 GET /uploads/{filename}으로 저장된 사진을 내려받는다. JPEG·PNG만 제공하고 X-Content-Type-Options: nosniff를 붙인다.

API-01 POST /diagnose

요청 파라미터

이름 위치 타입 필수 설명 예시
file body (multipart) binary O 사진. JPEG·PNG·HEIC/HEIF·DNG·WebP·AVIF leaf.jpg
crop_type query enum X 고추/무/배추. 사용자가 고른 작물 무
Idempotency-Key header string (1~128자) X 같은 요청 재전송 시 결과 재사용 UUID

작물을 폼 필드가 아니라 query로 받는 것은 처음 API를 만들 때 정한 방식을 그대로 유지한 것이다. 선택한 작물로 모델 점수를 바꾸지는 않는다. 모델이 고른 작물과 다르면 crop_mismatch=true로 알려 주기만 한다.

응답 (200)

이름 타입 설명 예시
id string (UUID) 진단 ID 3f9a1c02-…
disease_name string 1위 후보 이름 무 검은무늬병
confidence number (0~1) 분류 점수. 발병 확률 아님 0.46
top_predictions object[] 상위 3개 {name, confidence}
crop_type / selected_crop / predicted_crop string 또는 null 표시 작물 / 사용자 선택 / 모델 예측 무
crop_mismatch boolean 선택 작물과 예측 작물 불일치 false
category string disease 또는 normal disease
severity string DB에 정해 둔 병해 등급 low/medium/high. 사진에서 잰 진행 정도가 아님 medium
decision_status string normal/disease/crop_mismatch/confusion/low_confidence confusion
decision_reasons string[] 해당하는 이유 전부 ["confusion","low_confidence"]
policy_version string 판정 정책 버전 decision-v1:low=0.5
recapture object 또는 null 재촬영 안내 {region, instruction, margin, candidates[]} {"region":"잎 뒷면", …}
description, causes, prevention, management_actions string / string[] 병해 안내
pesticides object[] 진단 당시 농약 정보
prediction_mode string model/mock/browser/legacy model
model_version string 모델 파일 SHA-256 b0b0b4a2…
preprocessing_version string 전처리 규격 resize-224-imagenet-v1
image_url / refined_image_url string 또는 null 원본 / 재촬영 사진 /uploads/….jpg
save_status string saved 또는 failed saved
recovery_token string 또는 null 저장 실패 시 복구용
created_at / updated_at ISO 8601 UTC 시각

농약 항목에는 verification_status가 있다. PSIS 재동기화로 작물·병해별 사용 조건이 확인된 것만 verified이고, 나머지(legacy_unverified)는 희석배수·사용법·안전사용기준을 null로 내보낸다. 값이 없다고 0이나 임의 값으로 채우지 않는다.

API-02 POST /diagnose/{id}/refine

입력은 API-01과 같고, 경로의 ID는 1차 진단 ID다. 응답 형식도 같지만 recapture는 항상 null이다. 재확정 결과에서 또 재촬영을 요구하지 않는다. 새 이력을 만들지 않고 기존 이력의 결과와 refined_image_url을 고친다. 1차 분포는 initial_predictions로 계속 볼 수 있다.

API-03 POST /results/{token}/save

DB 저장에 실패했을 때 받은 recovery_token으로 다시 저장한다. 본문은 없다. 서버가 보관한 초안만 저장하므로, 클라이언트가 임의로 만든 진단 결과를 넣을 수는 없다. 다시 추론하지도 않는다.

API-04 GET /history

이름 타입 필수 설명 예시
page int ≥ 1 X 기본 1 1
size int 1~100 X 기본 20 20
crop_type enum X 작물 필터 배추
severity enum X 등급 필터 high

응답은 {items, total, crop_total, unfiltered_total, page, size}다. 필터 칩에 숫자를 보여 주려고 전체 건수, 작물 조건 건수, 최종 필터 건수를 따로 준다. 이건 Figma의 작물·등급 필터 12개 상태를 그대로 구현하다 보니 필요해진 필드다.

API-09 GET /ready

DB에 연결되고 실제 가중치와 DB 클래스 매핑이 맞으면 200, 아니면 503이다. 응답은 {status, database_connected, model_loaded, prediction_mode, version}이다. /health는 모델이 깨져도 200을 주기 때문에, Docker healthcheck와 배포 확인에는 /ready를 쓴다. 개발용 Mock 모드도 /ready에서는 503이다.

API-10 GET /capabilities

프론트가 업로드 전에 한도를 확인하는 데 쓴다.

{
  "upload": { "formats": ["JPEG","PNG","HEIC","HEIF","DNG","WEBP","AVIF"], "max_bytes": 104857600, "max_pixels": 210000000 },
  "crops": ["고추","무","배추"],
  "decision": { "version": "decision-v1", "low_confidence_threshold": 0.5, "confusion_margin": "(공개본 생략)",
                "second_photo_weight": "(공개본 생략)", "confusion_pairs": [[2,3],[4,5]] },
  "execution": { "server_inference": true, "browser_bundle_available": true,
                 "browser_inference": "device_validation_required", "voice_commands": false },
  "recovery_ttl_hours": 24
}

위 값은 Compose 기본 설정 기준이다. 한도는 환경 변수로 바뀔 수 있으니 실제 값은 서버에서 확인한다.

API-12 POST /offline/records

휴대폰에서 이미 진단한 결과를 서버에 올린다. 서버는 다시 추론하지 않고 prediction_mode=browser로 출처를 표시한다.

metadata는 JSON 문자열을 담은 폼 필드다.

필드 규칙
client_record_id UUID. 같은 ID로 같은 내용을 다시 보내면 중복 저장하지 않음
selected_crop 선택. 고추/무/배추 또는 null
model_version, preprocessing_version manifest 값과 일치해야 함
bundle_version 64자리 소문자 16진수. 형식 오류는 422, 형식은 맞는데 서버에 없는 묶음은 409
created_at 시간대 포함. 2000년 이후, 서버 현재 시각 + 5분 이하
predictions {class_id, confidence} 9개. ID 0~8이 한 번씩, 합계 1 ± 0.001
refined_predictions 선택. 있으면 refined_file도 있어야 함

오류 코드

모든 오류는 같은 형식으로 돌려준다.

{ "detail": "요청 항목을 확인해 주세요.", "code": "VALIDATION_ERROR", "retryable": false, "request_id": "c60fdccb-…" }

request_id는 응답 헤더 X-Request-ID와 같다. 사용자가 오류 화면을 캡처해 보내 주면 서버 로그에서 바로 찾을 수 있게 넣었다.

HTTP code 언제 화면 처리
400 EMPTY_IMAGE, INVALID_IMAGE, UNSUPPORTED_IMAGE_FORMAT 빈 파일, 깨진 파일, 이미지가 아님 다른 사진 선택 안내
400 REFINEMENT_UNAVAILABLE, MISSING_REFINEMENT_EVIDENCE 재촬영 대상이 아닌 진단, 1차 근거 없음 새로 진단
404 DIAGNOSIS_NOT_FOUND, RESULT_NOT_FOUND, NOT_FOUND 없는 이력·복구 결과·병해 이력으로 돌아가기
409 IDEMPOTENCY_CONFLICT 같은 키로 다른 사진을 보냄 새 키로 재시도
409 MODEL_VERSION_CONFLICT 1차 진단 이후 모델이 바뀜 새로 진단
409 DIAGNOSIS_CHANGED, UNSUPPORTED_BUNDLE 다른 요청이 먼저 수정함, 지원 안 하는 모델 묶음 다시 불러오기
410 RESULT_EXPIRED 복구 보관 시간(24시간) 지남 다시 진단
413 REQUEST_TOO_LARGE, IMAGE_TOO_LARGE, IMAGE_RESOLUTION_TOO_LARGE 100MiB 초과, 2억 1천만 픽셀 초과 크기 안내
422 VALIDATION_ERROR 파라미터 형식 오류 입력 확인
503 MODEL_UNAVAILABLE, DATABASE_UNAVAILABLE 모델·DB 준비 안 됨 잠시 후 재시도
503 IMAGE_STORAGE_UNAVAILABLE, RECOVERY_STORAGE_UNAVAILABLE, SAVE_FAILED 디스크 쓰기 실패 잠시 후 재시도
503 OFFLINE_BUNDLE_UNAVAILABLE 서버에 모델 묶음 없음 서버 진단 사용

retryable이 true인 오류에만 화면에 "다시 시도" 버튼을 띄운다. 오류 코드별 안내 문구와 버튼은 Figma 피드백 상태를 기준으로 화면에 적용됐다(10/17 고명준 커밋 "API 오류 코드별 Figma 지속형 안내 적용").

내부 인터페이스: CNN

ml_service.predict_all(image_path) -> list[(model_class_id: int, score: float)]   # 9개 전체, 내림차순
ml_service.predict(image_path, top_k=3) -> 상위 k개
ml_service.predict_pair(image_path) -> {class_id: score} 또는 None            # 보조 모델이 꺼져 있으면 None
  • 입력은 이미 검증·저장된 이미지 경로다. 전처리(224 리사이즈, ImageNet 정규화)는 모델 모듈 안에서 한다.
  • 출력은 9개 클래스 전체 분포다. 재촬영 융합에 전체가 필요해서 상위 3개만 주지 않는다.
  • 체크포인트에는 arch, num_classes, classes, model_state_dict가 있어야 하고, classes 이름은 숫자_이름 형식이어야 한다. 하나라도 어긋나면 모델을 쓰지 않는다.

내부 인터페이스: LLM 입력·응답 (박성호, #68~#70)

진단 결과를 LLM에 넘길 때는 DiagnosisLLMInput(schema_version 1.0)으로 바꾼다. 사진 URL과 내부 ID는 넣지 않고, 정의되지 않은 필드가 들어오면 거부한다(extra="forbid").

필드 타입 비고
disease_name, category, severity string
crop_type, selected_crop, predicted_crop, crop_mismatch 작물 불일치 정보
prediction_mode, decision_status, decision_reasons, policy_version 판정 근거
confidence, top_predictions[].confidence 0~1 실수 NaN·무한대 거부
description, causes, prevention, management_actions DB 안내
pesticides[].safety.phi_days, reentry_hours 0 이상 정수 또는 null 음수·실수 거부
recapture.margin 0~1 실수

응답은 LLMGuidanceResponse {text, source, fallback_reason}이다. LLM 호출이 10초 안에 안 끝나거나, 오류가 나거나, 빈 문자열을 주면 source="template"으로 바꾸고 미리 정해 둔 문장을 쓴다. 이때 fallback_reason은 unavailable/timeout/error/invalid_response 중 하나다. 템플릿은 판정 정책을 다시 계산하지 않고 이미 나온 판정을 그대로 문장으로 바꾼다.

Qwen의 기능 토큰(<hs_get_diagnosis> 등)을 이 응답으로 바꾸는 handler는 아직 없다. 기능 토큰 이름을 REST 경로로 착각하지 않도록, handler가 생기면 이 표에 별도 항목으로 추가한다.

4.4 통신 프로토콜 및 형식

구간 프로토콜 메시지 형식
화면 ↔ 백엔드 HTTP/1.1 REST 요청: multipart/form-data(사진), query string. 응답: JSON (UTF-8)
브라우저 ↔ 모델 묶음 HTTP 정적 파일 .onnx, manifest.json
백엔드 ↔ CNN·LLM 프로세스 내부 호출 Python 객체 / Pydantic 모델
백엔드 ↔ PSIS HTTPS XML·JSON (PSIS 형식)

gRPC나 Protocol Buffers는 쓰지 않는다. 호출 주체가 브라우저와 같은 보드 안의 에이전트로 제한되어 있으므로, REST와 JSON으로 충분하고, FastAPI가 Swagger(/docs)를 자동으로 만들어 줘서 팀원끼리 계약을 맞추기 쉬웠다.

요청 크기는 multipart를 해석하기 전에 ASGI 계층에서 먼저 막는다. 일반 요청은 파일 한도 + 64KiB, /offline/records는 사진이 두 장일 수 있어서 파일 한도 × 2 + 64KiB다.

4.5 인증 및 보안

접근 권한

현재 로그인과 API 인증이 없다. 이력도 모든 접속자에게 공유된다. 단말은 한 농가가 자기 보드에서 쓰는 구조라서 이번 학기에는 인증을 넣지 않기로 했다. 대신 백엔드 포트는 밖으로 열지 않고 프론트엔드(3000)만 공개하며, 브라우저는 같은 출처로만 호출하므로 CORS도 열지 않는다. 웹앱을 인터넷에 공개하려면 인증과 사용자별 이력 분리가 먼저 있어야 한다.

데이터 보호

  • 사진은 확장자나 MIME을 믿지 않고 실제로 디코딩해서 형식을 확인한다.
  • 클라이언트가 보낸 파일 이름은 저장에 쓰지 않는다. 서버가 UUID와 실제 형식으로 이름을 정한다.
  • HEIC·RAW 등 변환하는 사진은 EXIF·GPS를 복사하지 않는다. JPEG/PNG 원본에 남는 위치정보는 아직 develop에서 제거하지 못했다(5번 문서 결함 D-07).
  • 오류 응답에 서버 내부 예외나 인증 정보를 넣지 않는다. LLM 호출 오류도 내용 없이 error로만 기록한다.
  • HTTPS는 Compose 기본 구성에 없고, 배포할 때 앞단 프록시에서 붙인다. 휴대폰에서 카메라와 기기 진단(Service Worker)을 쓰려면 HTTPS가 꼭 필요하다.
  • PSIS API 키는 PSIS_API_KEY 환경 변수로만 받는다.
